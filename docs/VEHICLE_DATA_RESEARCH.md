# Данные об автомобиле, импорт и следующие функции

Краткий обзор источников и приоритетов для ShtBox. Проверено 30 сентября 2026 года; наличие продукта у провайдера не означает, что его можно использовать без договора или для личного бесплатного приложения.

## Что полезно добавить в приложение

У ShtBox уже есть журнал работ, дефекты на 3D-модели, напоминания, вложения, расходы, резервные копии, универсальный мастер импорта и режим «Чертёж» с полупрозрачным кузовом и штриховыми рёбрами геометрии. Наиболее практичные следующие шаги:

1. **Карточка идентификации автомобиля:** поколение/кузов, модельный год, рынок поставки, двигатель/код двигателя, коробка, привод, комплектация и источник каждого значения. VIN-декодирование должно предлагать результат для подтверждения, а не подменять его незаметно.
2. **План ТО по конкретной версии:** интервалы хранить вместе с рынком, кодом двигателя и ссылкой на источник; показывать дату проверки данных и позволять владельцу переопределить интервал. Нынешние общие шаблоны — ориентиры, не заводская рекомендация для каждого VIN.
3. **Бытовой учёт:** журнал пробега, топлива/зарядок и комплектов шин; документы с напоминаниями о сроке действия (например, HU/AU в Германии, страховка, гарантия); PDF-отчёт истории для мастерской или продажи.
4. **Осмотр и дефекты:** чек-листы сезонной/предпродажной проверки, фото «до/после», связь дефекта с работой и узлом на модели.
5. **Диагностика, позднее:** сначала безопасный импорт отчёта сканера и сохранение кодов/снимка условий; затем — только read-only OBD-II/EOBD. Универсальные коды не следует выдавать за диагноз: значения и проверки производителя могут отличаться.
6. **Разметка 3D с происхождением:** отдельная отметка точности для габаритов и панельных разрезов — «получено из источника», «оценено автоматически», «исправлено пользователем», «сверено с OEM». Для масок `panelRegions` указывать модельный год/поколение и источник.

Сначала разумно делать пункты 1–4 без внешних запросов: они сохраняют офлайн-режим и приватность. VIN/OBD интеграции потребуют явного согласия, проверки политики хранения и ясного указания источника; при отправке VIN третьей стороне его следует считать потенциально персональными данными в смысле GDPR.

## Насколько реально получить достоверные сведения

### Идентификация и основные размеры

- **NHTSA vPIC** предоставляет открытый API для VIN-декодирования и базовой информации производителя. Данные строятся на сообщениях производителей, но база ориентирована на автомобили для рынка США; для автомобиля европейской спецификации результат может быть неполным. API также ограничивает частоту запросов. Это полезный источник для североамериканских VIN, но не основной источник для немецкого парка.
- **TecAlliance OneDB / TecDoc** поддерживает поиск автомобиля по VIN и дереву «производитель → модель → вариант», а также связи автомобиля с деталями. Документация OneDB прямо указывает, что нужен статус клиента TecAlliance; формат API — REST/JSON. **TecRMI** отдельно предлагает структурированные интервалы обслуживания, технические характеристики, ремонтные инструкции и диагностические сведения с возможностью API-интеграции. Это самый очевидный мультибрендовый кандидат для европейского рынка, но коммерческий и договорный.
- **BMW Aftersales Online System** публикует API для идентификации автомобиля/опций по VIN и для сервисных данных. Доступ к API платный и требует onboarding квалифицированной третьей стороны. У BMW есть parts/service data в тех же системах, что AIR/ETK; это хороший узкобрендовый пилот, если проект когда-нибудь станет коммерческим.
- **Официальный CoC / документы одобрения типа ЕС** могут подтвердить базовые homologation-параметры конкретного типа/варианта: длину, ширину, высоту, базу и другие поля. Это сильнее случайной спецификации из каталога, но документ не содержит готовой 3D-сетки дверей и крыльев.
- **ALLDATA Europe** заявляет, что лицензирует оригинальные OEM repair/RMI данные напрямую у производителей, включая материалы для кузовного ремонта. Это ценный источник для проверки ручной разметки, но права на данные лицензируются; открытого универсального API или машиночитаемых CAD-разрезов для ShtBox не подтверждено.

### Точные дверные швы, контуры панелей и 3D

VIN-декодер обычно отвечает на вопрос «какая это машина/версия», а не «где проходит точная кривая шва двери в координатах конкретного GLB». В просмотренных публичных источниках не обнаружен бесплатный универсальный API, отдающий OEM CAD/3D-геометрию кузовных панелей.

Реалистичный путь к точности:

1. сначала сопоставить год, поколение, рынок и вариант через VIN/документы;
2. взять общие габариты из документа производителя/CoC, а конструктивные и кузовные сведения — из лицензированной OEM ремонтной документации;
3. сопоставить именно ту 3D-модель, которую загрузил пользователь: использовать реальные отдельные меши/названия/швы, если они есть;
4. при цельной оболочке разрезы всё равно подтверждать в мастере 3D вручную или по данным о швах, а не выводить только из VIN;
5. сохранять источник, версию и степень уверенности рядом с профилем модели.

В ЕС статья 61 Регламента 2018/858 предусматривает доступ независимых операторов к OBD и ремонтно-сервисной информации в машиночитаемом виде. Это не делает все данные бесплатным публичным API для любого приложения: решение Суда ЕС по делу C‑319/22 отдельно разъясняет, что право доступа не обязывает изготовителя создавать пользовательский интерфейс для автоматического поиска всех RMI-данных; для данных по заменяемым оригинальным деталям предусмотрена отдельная база. На практике нужны подходящий статус доступа и условия лицензии провайдера.

## Освещение и ощущение поверхности в 3D

В `Viewer` уже есть окружение `RoomEnvironment`/PMREM и мягкий набор fill/key/rim-света; это студийная схема, а не один физический источник. Усилить естественность можно позднее без тяжёлого real-time освещения: один большой key-свет сверху-сбоку, слабее fill с противоположной стороны, холодный/нейтральный rim и аккуратно настроенная экспозиция/roughness. Ползунок поворота key-света или 2–3 пресета «студия / дневной / осмотр» дадут больше контроля.

Для теней по умолчанию лучше начать с малозатратного contact-shadow blob и матовой полупрозрачной плоскости под автомобилем. Настоящие shadow maps можно сделать опциональными: на мобильных GPU они увеличивают цену рендеринга и требуют настройки размера карты/мягкости. Изменения света намеренно не закладываются в код этим этапом; мягкая плоскость и контактная тень добавлены отдельно.
