## 1. Что уже сделано хорошо (не переделывать)

- **Пакет «GLB + разметка»** (`Profile` v1 в `extras.shtbox`): модель и правки живут в одном файле, читаются
  в браузере и в CLI (`npm run import:model`), есть обмен пакетами и атрибуция (`asset.copyright`, credits).
- **Пайплайн в воркере** с бюджетом треугольников (`pipeline.ts`, `simplify.ts` на meshoptimizer),
  прогрессом и отменой; поддержка `EXT_meshopt_compression`, `KHR_mesh_quantization`,
  `KHR_materials_pbrSpecularGlossiness`, `KHR_materials_transmission`.
- **Честная неопределённость**: у каждой детали и границы — уровень уверенности (`confidence`),
  `provenance` отдельно помечает «авто / вручную / измерено», авторазбор пишет `autoNotes`.
  Это то, чего нет в большинстве готовых решений, и это стоит сохранять.
- **Поиск настоящих швов** (`seams.ts`): модель, уже разбитая на детали, не режется по прямым — панели
  берутся целиком, линии уточняются по кромкам, левые/правые детали сопоставляются по симметрии.
- **Правка вручную**: границы панелей, петли, маски панелей (`panelRegions`), режимы салона, текстуры
  (опционально), покраска и опускание стёкол (см. `ADDING_MODELS.md`, разделы 4–5).

## 3. Готовые решения и библиотеки (обзор)

### 3.1. Конвейер ассетов — **glTF Transform** (уже в зависимостях)

`@gltf-transform/core` и `extensions` уже стоят. Что не задействовано:

- **`KHRDracoMeshCompression`** + [`draco3dgltf`](https://www.npmjs.com/package/draco3dgltf) — декодирование
  Draco в воркере вместо ошибки. Это дороже всего по влиянию: у моделей, скачанных с Sketchfab и подобных
  сервисов, Draco-сжатие — обычный случай (то же решение применяют в других вьюерах glTF).
- **`optimize`-набор**: `dedup`, `prune`, `weld`, `quantize`, `instance`, `palette`, `reorder`, `simplify`,
  `textureCompress` (WebP/AVIF), `ktx` (KTX2/BasisU) — сейчас у нас свой `simplify.ts` и выборочная
  обработка; часть шагов дублируется, часть отсутствует. [CLI-справочник](https://gltf-transform.dev/cli)
- **`inspect` / `validate`** — можно вызывать в CLI-режиме `npm run import:model` и показывать отчёт
  «до/после» (байты, треугольники, текстуры, ошибки спецификации).

Вердикт: **брать**, это де-факто стандарт для glTF в JS. Лицензия MIT.

### 3.2. Форматы и загрузчики

- `three/addons` содержит `OBJLoader`, `FBXLoader`, `STLLoader`, `PLYLoader`, `USDZLoader` и др.
  ([док](https://threejs.org/docs/pages/FBXLoader.html)) — дешёвый способ принимать больше форматов без
  WASM, но без материалов/атрибуции качество разметки будет хуже.
- **assimpjs** (WASM-порт Assimp; есть готовый пример использования в
  [threepipe](https://threepipe.org/package/plugin-assimpjs.html)) — «один вход для 40 форматов»,
  конвертирует во внутренний формат и обратно. Тяжёлый (~2 МБ), но ленивая загрузка это терпит.
- **Online3DViewer** (MIT) — референс по поддержке экзотики (3mf, step, iges, brep, ifc) через
  `occt-import-js`/`rhino3dm`. Для нас это скорее источник идей: STEP/IGES-автомодели существуют,
  но конвертация CAD → сетка даёт «тяжёлые» модели.
- **fflate** (MIT, ~30 КБ) — принять `.zip` с `.gltf` + `.bin` + текстурами.

Вердикт: **брать** `.gltf`+zip (просто), assimpjs — опционально и лениво.

### 3.3. Операции с геометрией (если понадобится резать сложнее, чем плоскостями)

- **manifold-3d** (WASM, топологически надёжный kernel, npm `manifold-3d`) — булевы операции с
  гарантией watertight; именно его использует Babylon.js. [Обзор и бенчмарки 2026](https://polydera.com/algorithms/browser-mesh-boolean-libraries-2026):
  Manifold закрытый на 1000/1000 пар против 22/1000 у `three-bvh-csg`.
- **three-bvh-csg** — быстрый, но результат не всегда замкнут; на 200K+ треугольников медленнее Manifold.
- **three-mesh-bvh** — ускоренные лучи/расстояния/пересечения; полезен для «кисти», магнитов, измерения.
- **Ремонт сканов**: `@goodtools/meshrepair` (WASM, VCGlib), `meshfix-wasm`, `@meshinspector/meshlib` —
  убирают дырки, не-манифолд, дубли, делают decimate. Наши модели обычно «закрытые» дампы игры/сканы, где
  дырки есть; сейчас дырки просто игнорируются.
- **libigl / trimesh / pymeshlab** (Python) — мощная альтернатива для **CLI/офлайн-пути**:
  `npm run import:model` может вызывать python-скрипт, если он есть, и не тянуть ничего в браузер.

Вердикт: **manifold-3d или ничего**. Резать кузов булевыми дороже, чем плоскостями (см. §6), но для
«вырезать арку», «срезать подставку/пол», «отделить колесо» — самое надёжное.

### 3.4. 2D-логика для масок панелей и чертежей

Контуры панелей (`Profile.panelRegions`) — это 2D-полигоны в проекциях. Готовые библиотеки булевых
операций над полигонами дадут «объединить/вычесть/пересечь контуры», лассо-выделение и аккуратные
само-пересечения:

- `polygon-clipping` (MIT, Мартинес), `martinez-polygon-clipping` (MIT),
  `clipper2-wasm` (BSL-1.0) / `clipper2-ts`. [npm-выдача](https://www.npmjs.com/search?q=keywords%3Apolygon+clipping)

Вердикт: **брать `polygon-clipping`** — маленький, MIT, ровно наш кейс.

### 3.5. UI/редактирование в браузере

- **3D-Annotator** (MIT, React + three.js, [GitHub](https://github.com/3D-Annotator/3D-Annotator)) —
  кисть-сфера, лассо, полигон, по-пиксельное и по-треугольникам; ядро аннотации отвязано от React.
  Прямой источник приёмов для нашего `PanelEditor`.
- **TransformControls** (штатный addon three.js) — 3D-ручки для точек петель, плоскостей реза, осей
  открытия. Сейчас петли правятся числами и «кликните по точке».
- **Tweakpane** (тонкий GUI, работает с любым стеком; на нём же построен
  [three-inspect](https://github.com/threlte/three-inspect)) — для отладочной панели и «настройки
  материалов/сцены». `leva` рассчитан на React, у нас Preact — лучше Tweakpane.
- **online 3D-редакторы для инспекции** (ThreeMesh, Babylon Editor) — не наш кейс, но их приёмы
  (сечения, слои, аннотации, снапы) полезны как референс.

Вердикт: **TransformControls — брать** (это уже часть three.js), Tweakpane — только для dev-панели,
3D-Annotator — источник идей, не зависимость.

### 3.6. Автоматическая разметка: есть ли готовое?

Короткий ответ: **готового решения «разметить автомобиль» нет**.

- **Открывающиеся части (двери/капот/петли)** — активная область исследований: OPD/OPDMulti
  ([проект](https://3dlg-hcvc.github.io/OPD/), ECCV 2022, датасеты OPDSynth/OPDReal, код и веса),
  MOPD ([ACCV 2024](https://link.springer.com/chapter/10.1007/978-981-96-0963-5_6), код на GitHub),
  сводка — [Awesome-Articulated-Object-Understanding](https://github.com/dougefla/Awesome-Articulated-Object-Understanding).
  Это PyTorch/RGB-D-модели для кабин и бытовой техники, не для авто; в браузер без ONNX-конвейера и
  весов не встают. Но идеи (ось = крайняя линия + нормаль, «гипотезы движения» вместо чистых эвристик)
  применимы к нашим `seams.ts`/`analyze.ts`.
- **Части авто по изображению**: датасет `carparts-seg` (Ultralytics, CC BY 4.0, 23 класса: двери, стёкла,
  бамперы, капот, багажник, зеркала, колёса) и DSMLR Car-Parts-Segmentation; ApolloCar3D — 3D-детекция.
  Это про 2D-картинки, а не про разметку мешей.
- **Сегментация мешей по геометрии** (CGAL Surface_mesh_segmentation, libigl, TriMesh) — офлайн-путь:
  эти алгоритмы можно повторить у нас через dihedral-angle/feature-line детекцию, но это уже не библиотека
  «в браузер», а собственная работа.

Вердикт: логику разметки **оставляем свою**, усиливая её (a) геометрией кромок и симметрии,
(b) запоминанием правок пользователя, (c) — опционально и позже — ONNX-моделью на CPU с рендеров
модели (это отдельная задача с весом ~10 МБ, офлайн-PWA её терпит, но не сразу).

### 3.7. Источники моделей и лицензии

- **Sketchfab Download API**: >1 млн бесплатных моделей, glTF/GLB/USDZ, требуют логина пользователя,
  обязательна видимая атрибуция и указание CC-лицензии
  ([условия API](https://sketchfab.com/developers/terms), [Download API](https://sketchfab.com/developers/download-api)).
  Мы уже читаем `asset.extras` (автор/лицензия) — можно показывать атрибуцию в карточке модели и в
  PDF-отчёте.
- **Сканы**: Meshroom/AliceVision (MPL-2.0), COLMAP (BSD), Polycam/RealityScan — дают OBJ/GLB, из которых
  получаются «дырявые» меши; см. §3.3 про ремонт и §5 про нормализацию.

### 3.8. Варианты цветов и частей — KHR_materials_variants

Готовый glTF-механизм для «цвет кузова / диски / обивка» (three.js-плагин есть у сообщества:
[three-gltf-plugins](https://github.com/takahirox/three-gltf-plugins)). У нас покраска своя (шейдер),
но при экспорте пакета можно **писать** `KHR_materials_variants` — тогда модель откроется с вариантами
в других просмотрщиках. Недорого и полезно для обмена.

12. ⬜ **Тип кузова и класс авто по профилю** (наклон крыши, число дверей, длина) — авто-выбор `body`,
    чтобы меньше ошибочных «купе»/«хэтч»; результат идёт через существующий `provenance` с уверенностью.
13. ⬜ **Авто-подбор пресета** по названию/габаритам модели (остаток п. 6) и **обмен пресетами** между
    пользователями (экспорт `.json` уже есть).
14. ⬜ **Маски и петли прямо в 3D**: кисть по треугольникам, «вычесть из соседа», поворот петли гизмо,
    «проверка открытия» с анимацией зазора и подсветкой пересечений (остатки пп. 7–8).
15. ⬜ **Оптимизация пакета целиком**: `dedup/prune/quantize/instance` из gltf-transform при упаковке,
    экран «до/после» с визуальным сравнением бюджетов, `validate`/`inspect` в CLI-отчёте (остаток пп. 9–10).
16. ⬜ **ML-помощник (осторожно)**: ONNX `carparts-seg` на 3–5 рендерах модели → предложить зоны деталей
    с confidence; вес модели и лицензия (CC BY 4.0) — обязательны к учёту; включать по кнопке, офлайн.
    Только как «предложение», с пометкой `provenance: auto` и низкой уверенностью.
17. ⬜ **Проверка дефектов после правки модели**: метки дефектов живут в локальных координатах мешей —
    при повторном импорте/пересборке нужно уметь их переносить или помечать «нужно проверить».
18. ⬜ **Обмен и синхронизация моделей**: сейчас модель хранится только на устройстве; можно
    синхронизировать метаданные профиля (без GLB) и/или давать ссылку на скачивание пакета.
    Вспомогательное: показ атрибуции модели в карточке и в отчёте (по метаданным Sketchfab).

## 5. Что дало наибольший эффект (по факту)

- **P0**: Draco открыл модели из Sketchfab и подобных сервисов (это «обычный случай» для скачанных моделей);
  черновик и undo убрали потерю разметки при закрытии вкладки; проверки и линейка убрали «модель в дюймах
  и вверх ногами»; отчёт сделал импорт предсказуемым.
- **P1**: пресеты убрали повторную разметку той же машины; гизмо и маски убрали работу «на глаз» через
  ползунки; партия в CLI убрала ручной прогон по одному файлу; выбор детализации и JPEG для сохранённых
  текстур уменьшили пакет без новых зависимостей.
- **P2 — предлагаемый порядок**: подсказки по кромкам (11) → авто-тип кузова (12) → маски и петли в 3D (14)
  → оптимизация пакета целиком (15) → авто-пресет и обмен (13) → ML-помощник (16) → перенос дефектов (17)
  → обмен моделями (18).

## 6. Чего делать не стоит

- **Тащить Blender/USD/CAD-стек** в приложение: вес, лицензии, сложность несопоставимы с задачей
  «навести порядок в одной модели авто».
- **Резать кузов булевыми операциями целиком**: плоскости + настоящие кромки дешевле, предсказуемее и
  дают честные швы; булевы — точечно (арки, подставки, отделение колёс).
- **Полностью доверять ML-разметке**: ценность приложения — в честном `provenance` и уверенности;
  ML должен приходить как «предложение», а не как истина.
- **Своя реализация Draco/KTX2/упрощения**: всё это есть в gltf-transform/meshoptimizer.
